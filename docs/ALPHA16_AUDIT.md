# GeniaFolder alpha.16 — функциональный, UX и интерфейсный аудит

Дата: 2026-10-10. Ревизия исходного кода текущего `main` (`0.2.0-alpha.16`) и последнего успешного Windows CI. Это **статический аудит + анализ существующих smoke-tests**, а не подтверждение поведения в живом Explorer; перечисленные риски необходимо проверять отдельными тестами. Не объявлять alpha.16 production-ready для единственной копии ценных данных.

## P0 — исправить до любых новых destructive-функций

1. **Гонка между последней сверкой и удалением plaintext.** `VaultOnlyService.ActivateOrResumeAsync`: `VerifySourceMatchesVaultAsync` завершается **до** `MarkLockPendingAsync`, `Directory.Move` и `DeletePlaintextTreeOrThrow`. Если содержимое меняется в этот промежуток, свежие данные могут не попасть в snapshot и будут удалены. Требование: изолировать каталог от записи, затем повторно проверить изолированное содержимое; при несовпадении не удалять и обеспечить recovery. Добавить тест модификации непосредственно перед destructive phase и после source move.
2. **Конфликт вложенных managed/protected папок.** `MainWindow.AddManagedFolderAsync` не запрещает регистрацию вложенного каталога или родителя. `VaultEncryptionService.EnumerateSource` рекурсивно собирает вложенные каталоги, включая возможные профили/вложенные vault. Требование: однозначная политика ancestor/descendant, жёсткая блокировка опасных вложений перед шифрованием и Vault-only, тесты.

## P1 — высокий приоритет

3. **Невозможно обновить snapshot vault после правки файлов.** `VaultEncryptionService.BuildOrAdoptVerifiedVaultAsync` переиспользует существующий vault; прямой refresh/rotation отсутствует. `VaultOnlyService` безопасно откажет в блокировке, но пользователь не может штатно продолжить после редактирования. Нужна транзакционная замена snapshot с гарантированным сохранением старого валидного vault до commit.
4. **Потенциальная коллизия параллельных сохранений реестра.** `FolderRegistryService.SaveAsync` использует один фиксированный `folders.json.tmp` и не имеет сериализации. `Activated`/цвет/удаление/поиск одновременно вызывают сохранение. Требование: `SemaphoreSlim`, индивидуальный staging-путь или очередь транзакций, атомарный commit и тесты конкурентной записи.
5. **Осиротевший профиль после «Убрать».** `MainWindow.Remove_Click` удаляет строку из `folders.json`, но профиль и vault сохраняются; нет глобального списка vault без карточек и возврата по `FolderId`, если папка исчезла. Требование: «Архив профилей и vault», обнаружение orphan и импорт с проверкой паролем/Master.
6. **Master Recovery Key виден при вводе в восстановлении.** `VaultRestoreWindow.xaml`: `RecoveryKeyBox` — `TextBox`, а не `PasswordBox`. Предпочтительно скрытое поле с явным «Показать», очистка после использования и запрет ненамеренного раскрытия в screenshots/стримах. Не логировать секрет.
7. **Master Recovery подтверждается только галочкой.** `RecoveryKeyWindow` не требует повторного ввода или практической проверки сохранённой записи. `ProtectionService.VerifyMasterRecoveryKey` уже существует, но UI его не предоставляет. Требование: проверка введённого paper key после первичного создания, отдельная «Проверить Master Key» позже.
8. **Смена файловой identity может «штамповать» чужой каталог маркером до проверки.** `MainWindow.ReconcileFolderLocations` ставит `.geniafolder.id`, когда текущий путь существует и маркера нет, **до** сопоставления Windows ID и криптографической проверки. Требование: для уже известных профилей сперва проверить identity, не писать в непроверенный кандидат.
9. **Неоднозначные копии маркера иногда выбираются по истории без проверки других кандидатов.** `FolderLocationResolverService.TryResolve` сразу возвращает первое совпадение из `KnownPaths`, а ambiguous-copy guard выполняется лишь на этапе обхода остальных корней. Требование: детектировать multiple matches и предложить выбор + подтверждение.
10. **Потенциальная неустойчивость UI при повреждённом JSON/недоступном диске.** `ProtectionService.LoadProfile` и `FolderRegistryService.LoadAsync` десериализуют без изоляции ошибки на уровне карточки; асинхронные события `Loaded`/`Activated` обновляют экран. Требование: локализованное сообщение, безопасный read-only режим, не перезаписывать повреждённые данные.
11. **Нет полноценного E2E-теста цветов Explorer.** CI проверяет файловые свойства `desktop.ini`, но не фактически отображённый цвет живым Explorer. `FolderAppearanceService` многократно вызывает глобальное `SHCNE_ASSOCCHANGED` и COM-refresh окон. Нужны инструментированная диагностика изменения цвета/ресурса и ручная/GUI регрессия на поддерживаемых сборках Windows.

## P2 — UX/интерфейс/сопровождение

12. **«Защита» ≠ заблокировано.** Настройка FEK, создание encrypted copy, Vault-only и возврат plaintext разделены на несколько экранов; текстовые статусы и зелёные подтверждения иногда выглядят как «папка уже защищена», хотя plaintext доступен. Нужны явные этапы: `Без защиты` → `Ключи готовы` → `Резервная зашифрованная копия` → `Заблокировано (Vault-only)`.
13. **Несоответствие названий окна перемещения реальному действию.** `VaultRestoreWindow` в режиме `relocationVerification` продолжает показывать заголовок «Восстановить из encrypted vault» и подпись «Будет создано», хотя проверяет существующее содержимое и ничего не создаёт. Сделать отдельный режим UI/окно.
14. **Неполные граничные состояния кнопок.** `Убрать` в VaultOnly/LockPending кликабельна, но затем сообщает об отказе; вместо этого показывать disabled с объяснением. На списке недостаточно видны причины недоступности «Открыть»/«Цвет».
15. **Добавление папки без согласия изменяет её оформление и может затереть сторонний `desktop.ini`.** `AddManagedFolderAsync` немедленно вызывает `ApplyColorAsync(Blue)` и сохраняет Blue, независимо от текущих настроек. Предложить выбор цвета или режим «оставить значок как есть». Если требуется переоформление, сохранить/восстановить чужой customization.
16. **Сохранение папки не совпадает с сохранением информации о цвете.** Цвет в карточке берётся из `folders.json`; актуальный `desktop.ini` может отличаться после ручных операций/кэша Explorer. Показать состояние `применяется / подтверждено в metadata / Explorer не обновился` и отдельную команду диагностического refresh, избегать обещания фиксированных 1–2 секунд без измерения.
17. **Слежение не фоновое.** Проверка путей запускается при `Loaded` и `Activated`; пока окно не активировано, изменение может не отражаться. Уточнить UI: `Обновить состояние` и «Последняя проверка», либо добавить подписку на события FS с fallback сканированием.
18. **Нет явных действий «Проверить Vault», «Проверить Master», «Обновить Vault», «Управление архивом» из основного окна.** Пользователь должен помнить внутреннюю последовательность вкладок/окон.
19. **Много англоязычных служебных терминов в пользовательских окнах.** `Standard Protection`, `Vault-only`, `Encrypted vault`, `FEK`, `LockPending`, `plaintext`, `managed`. В основных кнопках — человеческие термины, технические детали — в `Подробнее`.
20. **Много модальных `MessageBox` и нет ненавязчивого журнала операций.** Реальное изменение цвета и подтверждение статуса могут занимать время; нужны inline-progress, notifications, история успешных/ошибочных действий, понятные recovery инструкции.
21. **`LockWindow` полагается на доставку события progress, чтобы определить старт необратимой фазы.** `_commitStarted` меняется только в UI `UpdateProgress` по строковым названиям этапов, а backend входит в commit независимо. При задержке событий кнопка отмены может ошибочно оставаться доступной. Передавать explicit typed commit signal/результат из сервиса.
22. **Нет матрицы стресс-тестов для реальных пользовательских файлов.** Расширить smoke на пустые/большие файлы, Unicode, глубокую вложенность, открытые файлы, файловые ссылки, full disk, прерванную запись реестра, потерю диска/профиля, multiple copies, конфликт вложенности, cancel-at-commit, изменение source during lock.

## Что уже реализовано и должно сохраниться

- AES-256-GCM шифрование чанками, аутентифицированный manifest, SHA-256 файлов, staging + publish, пароли к независимым FEK, общий бумажный Master Recovery Key.
- Vault-only с LockPending/recovery, запрет ссылок, сохранение vault при удалении plaintext, базовые security smoke-tests.
- Windows File ID + `.geniafolder.id` + история путей для перемещений; проверка cross-volume protected folder по authenticated vault.
- Цвета на `desktop.ini` и уникальном `.ico`; CLI-сборка и Windows CI.

## Предлагаемый порядок работ

1. **alpha.17 safety:** TOCTOU/commit signal, запрет опасных вложений, регистровый writer gate, защита от corrupted JSON.
2. **alpha.18 recovery:** orphan vault manager, backup/export профилей, верификация бумажного Master Key, скрытый ввод.
3. **alpha.19 functional:** crash-safe vault refresh и dirty/snapshot status; запрет stale lock до refresh.
4. **alpha.20 UX:** общая state machine, прозрачные кнопки, диагностика shell colors, отдельный rebind UI, GUI-тесты.

**Текущий тестовый статус:** workflow Windows Build собирает решение и запускает пакетные security smoke-tests; по последнему известному запуску для `0.2.0-alpha.16` CI успешен. Успешный CI не подтверждает отсутствие перечисленных гонок и реальный цвет значка в Explorer.
